01项目概述

1.1 一句话定位

ItemLife 是一个「以物品为视角」的个人 / 家庭记账 Web 应用：既做常规的收支记账与资产余额管理，又把每一笔支出与具体物品（及其配件）关联起来，让用户看清「一件东西从买到用完，总共花了多少钱、每天成本是多少」。

1.2 核心价值

记记账

账户资产余额管理、自定义分类、收入 / 支出 / 转账、收支与总资产趋势看板。

物物品

支出与物品关联，配件库存（如 12 个刷头用了 2 个）与持有成本核算，独立的物品看板。

家家庭

邀请码组建家庭，数据域（个人 / 家庭）自由切换，家庭共享账本与物品库。

1.3 关键设计原则

  • 移动优先（Mobile First）——先在 360px 宽度上把体验做对，再向上适配平板与桌面，而不是把桌面版缩小。
  • 单一数据源（Single Source of Truth）——流水表 transactions 是金额的唯一权威来源；账户余额、物品成本、看板统计均由它派生，避免多份数据对不上。
  • 凭据绝不明文——密码、TOTP 密钥、恢复码、刷新令牌全部经过哈希或加密后才落库（详见第 7 章）。
  • 安全默认（Secure by Default）——注册即引导开启 MFA；接口默认要求鉴权；越权校验内置在数据访问层。
  • 一键部署——目标机器只需安装 Docker，执行 docker compose up -d 即可完成全部服务的构建、初始化与启动。

03技术选型与论证

选型总原则：全栈 TypeScript 共享类型、移动端优先、容器友好、单人可维护。数据库按需求方指定采用 MySQL 8。

层次选型理由
前端框架 Vue 3（Composition API）+ TypeScript + Vite 推荐 响应式系统对「账本数据频繁联动刷新」场景心智负担低；SFC 单文件组件适合单人快速迭代；Vite 构建快、产物体积小；中文社区资料充足。
UI / 样式 Tailwind CSS + 项目内无头组件已采用 断点前缀（sm: md: lg:）用于移动优先响应式布局；下拉与弹层由 AppSelect / AppModal 自实现，统一键盘、遮罩和动画行为。
状态 / 数据 Pinia + Axios（预留 TanStack Query） Pinia 管会话、数据域与账本缓存；页面通过 Axios 并发拉取服务端数据，写入后显式刷新。当前数据量下保持状态路径简单。
图表 ECharts（路由内延迟加载） 进入看板或物品详情时再加载图表代码，首屏不阻塞；同时提供表格替代视图，兼顾移动端与可访问性。
后端框架 NestJS（Node.js LTS + TS）推荐 模块化架构（Auth / Ledger / Item / Family / Dashboard 清晰分层）；与前端共享 DTO 类型定义；Passport 生态覆盖 JWT 认证；内置 Guards / Interceptors / Pipes 体系，安全校验有规范落点；容器镜像轻量（约 150MB）。
ORM / 迁移 Prisma + MySQL 8.4 Schema 即文档、类型安全查询（编译期发现字段错误）、迁移工具 prisma migrate 适合容器化启动流程；参数化查询天然防 SQL 注入。
认证与 MFA Passport-JWT + otplib（TOTP，RFC 6238）+ argon2 + qrcode otplib 是 Node 生态 TOTP 事实标准，兼容 Google Authenticator / 微软 Authenticator；argon2 为 OWASP 首推密码哈希算法。
缓存 / 限流 Redis 7 + @nestjs/throttler 登录限流、TOTP 防重放时间窗、刷新令牌与幂等键状态；看板 v1 直接聚合以保证写入后立即一致。
Web 服务器 Nginx（alpine） 托管前端静态产物 + 反向代理 /api；gzip、缓存头、SPA 路由回退一站配置。
容器编排 Docker Compose 需求明确要求；单机自托管场景最合适的复杂度；healthcheck + depends_on 保证启动顺序。
测试 Vitest（单测）+ Playwright（E2E，多视口） Playwright 可直接在 375 / 768 / 1440 三种视口跑同一套用例，验证响应式行为。

关于数据库：按需求方指定采用 MySQL 8.4 LTS（InnoDB + utf8mb4），金额使用 BIGINT 存储「分」而非浮点；MySQL 8 的窗口函数与 CTE 足以支撑看板聚合查询。

3.1 为什么金额存「整数分」

浮点（FLOAT / DOUBLE）存在二进制表示误差（0.1 + 0.2 ≠ 0.3），记账系统绝不可用；DECIMAL 虽然精确，但在 ORM 与 JS 之间转换时需要额外的小数处理库。统一以「分」为单位的 BIGINT 存储与传输，在前端展示层再除以 100 格式化——全链路只做整数运算，从根本上消除精度问题，这也是主流支付系统的通行做法。

04系统架构设计

4.1 总体架构

前后端完全分离：前端为纯静态 SPA，后端只提供 REST/JSON API。生产环境中两者由 Nginx 统一入口（同源部署），既简化了 CORS 与 Cookie 策略，也便于将来拆分为独立域名或加 CDN。

4.2 请求链路

  1. 浏览器请求 https://host/ → Nginx 返回 SPA 静态资源；
  2. SPA 发起 https://host/api/v1/... → Nginx proxy_pass 到 api:3000（同源，无跨域问题）；
  3. API 通过 Guard 校验 JWT → 业务模块校验数据域权限（个人 / 家庭）→ Prisma 访问 MySQL；
  4. Token 中 mfa:true 声明代表该会话已完成两步验证，未完成的会话仅允许访问 MFA 相关端点。

4.3 关键技术决策记录（ADR 摘要）

决策结论与理由
前后端同源（Nginx 统一入口）免 CORS 配置、Cookie 策略简单、防 CSRF 更容易；开发期用 Vite Dev Server 的 proxy 模拟同源。
金额以整数「分」传输前后端 JSON 中金额字段一律为整数分（如 40000 表示 ¥400.00），杜绝浮点误差。
统一「数据域」模型账户 / 分类 / 流水 / 物品四类数据共享 owner_type('user'|'household') + owner_id 双字段归属模型，一套权限逻辑覆盖全部业务表。
软删除 + 回收站记账数据误删代价高，全部业务表使用 deleted_at 软删除，回收站保留 30 天。
时间统一 UTC数据库存 UTC（DATETIME(3)），API 传输 ISO 8601，前端按用户时区渲染。
主键采用 UUID v7时间有序、不可枚举、便于未来多端离线写入合并；MySQL 中以 BINARY(16) 存储兼顾索引性能。

5.3 数据完整性约束

  • 所有外键建立真实 FOREIGN KEY 约束（InnoDB），删除父行前先校验子行；
  • 金额字段统一 BIGINT，服务层 DTO 校验 amount_minor ≥ 0 且为整数；
  • owner_type 用 ENUM 约束取值范围，(owner_type, owner_id) 复合索引覆盖全部业务查询；
  • 转账两行记录在同一数据库事务中写入，任一行失败则整体回滚；
  • 物品分摊（服务层校验 + 事务内写入）：Σ(transaction_items.amount_minor) ≤ transactions.amount_minor，超出即拒绝；同一流水下 item_id 唯一；单物品且未指定金额时 amount_minor 置 NULL，语义为「继承流水金额」；
  • 利息入账幂等：accounts.interest_posted_at 与利息流水一一对应，同一结息周期重复触发不会生成两笔（详见 8.5）；
  • 软删除行的唯一约束通过 deleted_at IS NULL 生成列方案处理（如账户名在同一数据域内不重复）。

流程 A · 注册

7.3 会话与令牌策略

Access Token（JWT）

有效期 15 分钟；HS256 签名（密钥 ≥ 256 bit，环境变量注入）；载荷仅含 sub / sid / mfa / exp，不含邮箱等隐私；前端存内存（不落 localStorage，缩小 XSS 影响面）。

Refresh Token

HttpOnly + Secure + SameSite=Lax Cookie，仅 /api/v1/auth 路径可见；14 天有效；每次刷新即轮换（旧令牌立即吊销）；检测到已吊销令牌被复用 → 整族吊销并强制重新登录（令牌盗用响应）。

TOTP 防重放

每个用户的 TOTP 验证记录「最后成功时间步」（Redis + DB 双写）；同一 30 秒窗口内第二次提交一律拒绝，防止动态码被截获后重放。

登录失败防护

按「账号 + IP」双维度 Redis 计数：15 分钟内 5 次失败 → 指数退避锁定（1min → 5min → 15min）；全部失败记录写入审计日志；响应统一模糊化（不区分「密码错」与「验证码错」）。

08核心业务逻辑设计

8.1 记账与账户余额

余额派生规则（单一数据源）：账户当前余额不由人工维护，而是实时从流水派生：

余额(账户) = initial_balance + Σ(income) − Σ(expense) + Σ(transfer_in) − Σ(transfer_out)
// 全部取自 transactions 表，deleted_at IS NULL，按 account_id 聚合
  • 净资产 = Σ(全部账户余额)，投资类账户单独着色展示；
  • 转账：同一事务写入 transfer_out（转出账户）与 transfer_in（转入账户）两行，共享 transfer_group_id；编辑 / 删除时成对联动；
  • 性能：金额聚合走覆盖索引 (account_id, type, amount_minor)；数据量大后引入每日快照表 account_balance_daily（当前规模不启用）。

8.2 物品与配件成本模型 核心特色

以需求原例说明：电动牙刷本体 400 元；同时购入 12 个替换刷头，单价 20 元；目前已用掉 2 个刷头；物品持有 100 天。

¥640.00
① 总支付金额
400 + 12×20
¥440.00
② 当前持有成本
400 + 2×20
¥4.40
③ 日均持有成本
440 ÷ 100 天
¥200.00
④ 剩余配件价值

指标定义

① pay_total = item.purchase_price + Σ(accessory.unit_price × total_qty)
「总支付金额」：为这件物品实付的全部金额（含全部配件库存）

② hold_cost = item.purchase_price + Σ(accessory.unit_price × used_qty)
「当前持有成本」：物品 + 已用掉的配件——"到现在真正花在这件东西上的钱"（核心三指标之一）

③ daily_hold_cost = hold_cost ÷ held_days
held_days = today − purchase_date + 1（≥1）
「日均持有成本」：需求中"物品+两个刷头的价格/物品持有日期"的落地公式

④ remaining_stock = Σ(accessory.unit_price × (total_qty − used_qty))
「剩余库存价值」：还没用掉的配件值多少钱（可理解为"预存资产"）

⑤ projected_daily = pay_total ÷ expected_lifespan_days　（可选，仅当用户填写预期寿命时显示）

展示设计（核心三指标）：总支付金额、当前持有成本、日均持有成本 为固定展示的核心指标。物品卡片列表中，移动端可精简展示（至少保留 总支付 + 日均持有成本 两项）；进入详情页必须完整显示全部指标（含当前持有成本、剩余配件价值）与「成本演进折线图」（横轴时间，纵轴累计消耗成本，配件每使用一枚出现一个台阶）。

口径已确认：「物品 + 两个刷头的价格 ÷ 物品持有日期」按 (物品价 + 已用配件价) ÷ 持有天数 落地（即 hold_cost ÷ held_days = 440 ÷ 100 = ¥4.40/天）。公式封装为独立 CostService 并参数化，后续如需调整口径（例如改为 pay_total ÷ held_days）仅改动一处。

物品与记账的联动（多物品分摊）

  • 一笔流水可关联 1～N 个物品，关联与分摊统一走 transaction_items 表（见 5.2 ⑧），每个物品可单独指定分摊金额；
  • 单物品简化写法：不填分摊金额时 amount_minor = NULL，表示继承整笔流水金额（仅单物品场景允许）；
  • 未分摊差额：Σ分摊金额 ≤ 流水金额，差额在流水详情页单独标注「未分摊」（如 100 元流水仅分摊 30 + 20，剩余 ¥50 为未分摊）；
  • 新建物品统一从“记一笔”的物品清单创建；物品页只负责查看、状态和库存管理；
  • 购买配件 = 一条支出流水中的附加物品分摊 + 在 item_accessories 增加一批库存；
  • 数据一致性：成本金额以流水分摊为权威来源，配件表承载数量和单件分配；删除任一侧都同步调整另一侧。

8.5 账户利息自动计算 增强

储蓄 / 理财类账户可配置年化利率，系统按日计息、周期性入账，自动生成利息收入流水，无需手工记账。

账户计息配置（accounts 表，见 5.2）

字段取值说明
interest_rate_bpINT，如 175 = 1.75%年化利率（基点，1bp = 0.01%）；NULL = 不计息
interest_freqmonthly / quarterly / yearly结息周期，默认 monthly（每月入账一次）
interest_posted_atDATE上次结息日，同时作为幂等标记（见下）

计息公式（单利 · 按日累计）

利息 = Σ(每日余额 × 年化利率 ÷ 365)　// 周期内逐日累加
余额口径与 8.1 一致（由流水实时派生）；结息入账后，新余额从次日起参与计息

入账与幂等防重

  • 每日 @Cron 扫描已配置账户：当 today ≥ interest_posted_at + 结息周期 时，计算该周期利息并写入一条 type=income 流水（系统分类「利息收益」、system_tag=interest、归属该账户）；
  • 幂等：入账成功后将 interest_posted_at 推进至结息日；任务重跑 / 服务重启后先校验该字段，同一周期绝不重复入账；
  • 手动结息：POST /accounts/:id/interest/run 支持随时预览并确认入账（按实际天数计息），与自动结息共用同一计算服务，口径一致；
  • 口径说明：v1.0 采用单利（不计复利）；利率变更从下一计息区间起生效；利息流水在趋势看板「收益」指标中独立呈现（见 8.4）。

10.3 Compose 网络设计 回答你的问题

是的——同一个 compose 文件中的所有服务，默认会自动加入同一条以项目名命名的桥接网络 <项目名>_default（本项目即 itemlife_default），相当于自动组建了一个内部局域网：

  • 服务名即 DNS：容器之间直接用服务名互访（mysql:3306、redis:6379、api:3000），无需关心容器 IP——本方案的 DATABASE_URL / REDIS_URL 正是这么写的；
  • 默认隔离：该网络只存在于本项目内，与宿主机上其它 Docker 项目互不相通；ports 未声明的端口只在该网络内可见，外部无法直连；
  • 出网行为：默认 bridge 网络允许容器访问外网；可加 internal: true 完全切断出网。

本项目的做法（不依赖默认网络，显式声明两层分段）：frontend（仅 web，承接外部反向代理回源）与 backend（web / api / mysql / redis 四者互通，见 10.2 底部 networks 段）：

  • backend 设置 internal: true——mysql / redis / api 无法主动访问外网，数据面攻击面最小；
  • web 同时挂在两条网络上：对外发布端口走 frontend，与 api 通信走 backend；
  • 由于网络按项目隔离，未来同机部署多个环境（dev / prod）也不会互相串通。

10.5 内网部署与外部反向代理对接 已确认

部署形态已确认：本系统在内网以 Compose 运行，公网访问由容器外部你自备的路由 / 反向代理提供。完整链路：公网用户 → 你的反向代理（TLS 终止）→ 宿主机 :80 → web 容器（nginx）→ backend 网络 → api 容器。

外部代理侧（你配置）
  • 将公网域名路由回源到本机 :80（TLS 在外层终止；默认回源走 HTTP，如需 HTTPS 回源可在 web 容器自行挂载证书并放行 443）；
  • 透传请求头：X-Forwarded-Proto、X-Forwarded-For（或 X-Real-IP）、X-Forwarded-Host，并保留 Host；
  • HSTS 与证书续期由外层代理统一负责；如路径经过 CDN / WAF，注意放行 Cookie 与 Authorization 头。
应用侧（已内置适配）
  • API 开启 trust proxy——限流与审计按真实客户端 IP 计数，而非代理 IP；信任跳数由 TRUST_PROXY 控制（默认 2 = 外部代理 + web 容器；不经外部代理时置 1）；
  • Cookie 的 Secure 依据 X-Forwarded-Proto 动态设置：经公网 HTTPS 访问自动 Secure，内网 HTTP 直连可降级，两种方式都能正常登录；
  • HSTS 不在内层重复下发，避免内网直连被强制跳转 HTTPS。

内网直连（可选）：不经外部代理、在内网直接访问 http://<主机IP>/ 同样可用（Cookie 自动降级为非 Secure）；安全要求高时建议在外部代理或内网入口统一提供 HTTPS。

13.2 技术风险与对策

风险等级对策
MySQL 中以 BINARY(16) 存 UUID 的 ORM 映射复杂度中Prisma 层统一封装 Bytes 编解码工具函数；如开发中发现摩擦过大，可降级为 CHAR(36)（数据量级下性能差异可忽略）
TOTP 依赖设备时钟，用户手机时间漂移导致验证失败中服务端放宽 ±1 个时间窗（±30s）；绑定页提示校准时间；提供恢复码兜底
用户丢失手机 + 恢复码 → 无法登录中文档明确恢复码保管责任；v1.1 可加「备用邮箱重置」流程
看板聚合查询随数据量增长的性能低个人 / 家庭记账量级（万级流水）MySQL 索引完全够用；预留日快照表与 Redis 缓存方案
单机部署无高可用低自托管场景接受；备份 + 快速重建即可满足 RPO
Tailwind + 自研组件的表单 / 日期组件开发量中复用项目内 AppSelect、AppModal 与统一字段样式；新增复杂控件前先验证原生与现有组件能否满足。
