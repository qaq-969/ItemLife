记物与记账的联动调整方案

让「一笔采购」只录一次：流水负责记钱，物品负责记用法

基线：beta-czw 5eb6329（M1 / M2 / M3 已完成） 日期：2026-09-23 状态：待拍板 Q7–Q9

01一句话结论

现在这套系统里，同一笔花出去的钱，被要求在两处分别登记，而这两处之间没有任何绑定关系：物品档案自己存一份「本体价」，流水自己存一份「金额」，谁也不会替谁核对。用户录完物品还得再去「记一笔」重录一遍金额，数字对不上时系统一声不吭。

建议调整为：「记一笔」是花钱的唯一入口，物品的成本从它派生；物品侧只保留「这东西怎么用、用了多少」，不再单独保管一份金额。配件库存的语义顺带被厘清——它是「已经付了钱、但还没用掉」的那部分。

收益：买牙刷 + 刷头这套动作，从「录物品 → 再去记一笔 → 手动保证两个金额一致」变成一次录入；物品的「总支付金额」与关联流水的金额按构造相等，不再需要用户人工对账。

02现状：一件事，两条互不相干的链路

以设计报告第 12 章的验收用例「牙刷 ¥400 + 12 个刷头（¥20/个，已用 2 个）」为例，当前用户必须这样做：

  1. 底栏「＋记一笔」→ 支出 ¥400 → 选账户、分类 → 保存。（账户余额 −400 ✓）
  2. 底栏「物品」→「录入物品」→ 再手输一次本体价 400、购买日期、预期寿命。
  3. 同一页再加一行配件批次：名称「替换刷头」、单价 20、总数 12、已用 2。（12×20=240 的这笔钱，账户里还没有对应流水）
  4. 要补上刷头的账，再回「记一笔」录一笔 ¥240——此时系统不会提示这条流水跟刚才那 12 个刷头有关系。

结果是同一个物品在详情页上同时存在两套数字：

物品卡片（由本体价 + 配件批次算出）

¥640.00

总支付金额 = 400 + 12×20；当前持有 ¥440.00

关联流水区（由 transaction_items 反查）

¥400.00

只有本体那一笔（如果用户记了）；刷头那 240 元不在这里

两个数字都对，但没有一个机制保证它们一致：用户如果手滑把本体价填成 380，或漏记刷头流水，系统会一直保持沉默。这就是「混乱」的直观来源。

04根因

① 事实来源重复

同一笔钱同时存在于 items.purchase_price_minor 和 transactions.amount_minor，两个可写字段、两处录入。

② 缺「绑定」这一层

transaction_items 只是弱引用（可空金额、仅用于展示），它不是「这笔钱就是这个物品的成本」的声明。

③ 报告自身口径打架

§8.2 公式基于物品档案，§6.3 示例却按流水算未分摊额。实现只能二选一，另一处变成孤儿。

另外还有一处小口径冲突：报告 §5.2⑧ 举的分摊例子是「牙刷 ¥400 + 12 个刷头 ¥240」，但刷头在设计上是配件（accessory）而不是物品（item），当前的 transaction_items 只能指向 item——也就是说，系统目前根本无法表达「这一笔 ¥640 里，240 是买刷头的钱」。

05目标模型（推荐方案 A）

5.1 一张图

持有成本 ¥440.00 = ¥640.00 − ¥200.00

5.2 三条规则

  1. R1 · 花钱只在一处发生。任何一笔支出都只作为流水存在；物品与配件批次不再单独保管金额，只保管「用掉了多少」。
  2. R2 · 物品的钱 = 分摊到它的流水之和。一笔流水可拆给本体、配件或多个物品；同一物品也可以有多笔流水（本体首购 + 配件补货 + 同款再买）。
  3. R3 · 成本公式不变。设计报告 §8.2 的五个指标原样保留，只是公式里 purchase_price 这个变量的来源，从「用户手填」改为「Σ 本体分摊」。

5.3 两个可自动校验的不变量

① pay_total = Σ(绑定到本物品的全部分摊：本体 + 配件)
② remaining_stock = Σ(配件.单价 × (总数 − 已用数))
③ hold_cost = pay_total − remaining_stock　← 与 §8.2「本体 + 已用配件」恒等

等式 ③ 值得单独说一句：它把「总支付」和「持有成本」变成了同一根数轴的两端——付出去的钱，减去还没用掉的部分，就是「到现在真正花在这件东西上的钱」。这句话既是成本口径的自然解释，也是可以直接写进冒烟断言的一致性校验。

「不挂流水的物品」仍然允许。别人送的、或者只想记个价看日均成本的东西，可以不关联任何流水；此时成本退回用手填的本体价计算，详情页打一个明确标记「未关联流水 · 金额为手填」，并提供一键补记入口。这是兼容历史数据的必要退路，也让方案 A 保持了灵活性。

成本角度其实只有两种行为

全额立即计入：body、fee —— 钱花出去就变成「持有成本」，没有库存形态。

先计总支付、未用部分挂库存：accessory —— 买了 12 个只用 2 个，另外 10 个还值 ¥200，不算「已经花在这件东西上」。

所以恒等式 hold_cost = pay_total − remaining_stock 对五种情形全部成立，§8.2 的公式一个字都不用改。

① pay_total = Σbody + Σfee + Σaccessory(单价 × 总数)
② remaining_stock = Σaccessory(单价 × (总数 − 已用数))
③ hold_cost = pay_total − remaining_stock　← 加 fee 后恒等式依然成立

「分类」和「物品归属」是两个并行维度，不是重复记账。

· 分类（日用百货 / 餐饮 / 维修）回答「这笔钱花在什么性质的事上」——账本的基本维度，任何流水都要有（转账除外）；

· 物品归属（body / accessory / fee / link）回答「这笔钱该摊到哪件东西头上」——成本归集维度，永远可选。

同一笔 ¥640 会同时出现在「本月消费 +640」（分类口径）和「该物品总支付 +640」（物品口径）。这不是重复计算，是同一笔钱的两种视图；物品详情页与流水列表互相标注来源流水，可双向跳转核对。

5.5 成本演进折线要跟着扩一处输入

现在的台阶只来自「配件使用 / 撤销」（accessory_usages）。加入 body / fee 流水后，每一笔成本类流水的发生日也应在曲线上落一个台阶（首次采购日就是折线起点）。这样「第 200 天换电池 ¥50」会在图上直观抬起一格，日均持有成本随之从 ¥4.40 变为 ¥4.90——用户能一眼看出「这笔附加费用把日均推高了多少」。

三条边界，方案里先说清楚：

· 耗材还是附加费用？判定规则：有「个数」、会分次使用、关心还剩几个的走「配件」（有剩余价值，更精确）；花掉就没了、不关心剩几个的走「附加费用」。系统不替用户猜，两个选项都摆在用途下拉里；选错了可在物品详情页改归类。

· 退款 / 退货：v1.0 不支持负数分摊。退货请在物品详情页解除或修改该笔关联流水，或直接删掉这笔流水，成本随之回落；role=refund + 负分摊列为 v1.1 候选。

· 别人送的 / 不想记钱：不关联任何流水，成本退回手填价并标记「未关联流水」。

06交互调整（四个页面）

6.1 记一笔：主表单不动，只在下方加「物品归属」

五个场景（普通账 / 新物品 / 耗材 / 附加费用 / 仅关联）共用同一个页面，逐行展开见 §5.4。要点是默认路径零额外操作：不碰物品区块，就是一笔普通账。

「物品归属」区块由两条按钮驱动，每加一行就是一条 transaction_items：

「记到已有物品」

新增一行：选物品 → 选用途（本体追加 / 配件补货 / 附加费用 / 仅关联）→ 填金额。

选「配件」时会展开批次选择：挑已有批次，或当场新建一个（填总数，单价由「金额 ÷ 总数」反算）。

「这是一件新物品」

内联展开小表单：名称 / 分类 / 预期寿命，金额自动带入该行。

保存后流水与物品一起落库，物品的购买日期直接取流水发生日期，不用再手填。

什么都不点

普通账。金额 + 分类 → 保存，与今天完全一致。

现有用户的操作习惯不受任何影响。

一笔流水可以混合多种去向，例如超市一笔 ¥730 拆成：新建物品「电动牙刷」本体 ¥400 + 该物品刷头补货 ¥240 + 已有物品「洗发水」追加 ¥30 + 未分摊 ¥60。未分摊部分照旧在详情页标注。

6.2 录入物品：加「这笔钱记过没有」

( ) 已经在别处记过    从最近流水中选择 [ 超市采购 ¥640 · 09-20 ▾ ]  / 暂不关联

选第一项：保存后一条流水 + 一个物品同时落库，双向绑定，两边金额按构造相等。
选第二项：绑定已有流水，系统自动取该流水的分摊金额作为本体价。
都不选（暂不关联）：保留手填价，详情页标记「未关联流水」。

6.3 物品详情：把两套数字合并成一条主线

现在

· 总支付 ¥640.00（手填的本体价 + 配件）

· 关联流水 −¥400.00（另一套数字）

两者无关联，靠用户自己理解

调整后

· 总支付 ¥640.00 = 采购流水合计 ✓

· 构成：本体 ¥400.00（流水 #1）+ 刷头 12×¥20 ¥240.00（流水 #1）

· 已用 2 个 → 持有成本 ¥440.00，剩余库存 ¥200.00

没有流水的部分标黄并给补记入口；流水金额与分摊不一致（历史数据）时显示差额，而不是静默。

6.4 配件批次：入库时可挂流水

详情页「添加批次」弹层增加可选块：

  • 「同时记一笔支出」→ 填总数 + 总额，系统反算单价（¥240 ÷ 12 = ¥20/个），并生成一笔支出流水；
  • 「已记过，选择流水」→ 从最近支出中挑一条，取其分摊金额反算单价；
  • 「暂不关联」→ 维持现状（手填单价），批次上标记「未关联流水」。

一致性校验：当批次绑定流水后，若 单价 × 总数 ≠ 该批次的分摊金额，服务端返回 409 并说明差额，而不是默默接受两套数字。

08实施路径（三步，每步都可独立交付与验收）

Step 1 · 只加不删

加字段与迁移；前端补三处入口（记一笔新建物品、录入物品同步记账、批次挂流水）；详情页显示「已关联 / 未关联流水」标记。

老数据零影响，可随时回滚

Step 2 · 切口径

CostService 的输入源改为「有绑定用分摊之和，无绑定用回退价」；成本演进折线的台阶来源补上「body / fee 流水的发生日」；两条不变量写进 smoke:items；物品详情页把两套数字合并成一条主线。

此步完成后，混乱感才真正消失

Step 3 · 收口

把回退价在 UI 上标注为「仅历史/未关联时使用」；新物品默认走流水创建；同步修订设计报告 §6.3 与 §8.2 的措辞，消除口径打架。

回归基线不受影响：现有 smoke:items 57 项中，凡是「无绑定流水」的用例应当继续绿（走回退价），这正是 Step 2 的验收标准——老数据一个数不变。

09备选方案与取舍

方案做法评价
A · 流水为事实来源
推荐		 一处录钱，物品派生；成本公式保留，变量来源改为分摊之和 根治「录两遍」；顺带让一笔流水能表达「本体 + 配件」的拆分；代价是要加三个字段与迁移
B · 双轨 + 对账提示
最小改动		 模型不动，只在物品详情页显示「物品价 ¥400 vs 关联流水 ¥380，差 ¥20」并给补齐按钮 改动最小、一周内可完成；但两处录两遍的根因仍在，用户依旧要在两个 Tab 之间搬运同一个数字
C · 物品为唯一入口
反向		 「记一笔」里去掉物品选择；买物品一律从物品页走，自动生成流水 与报告 §8.2 的核心用例冲突：一笔超市采购要拆到多个物品上，从物品页发起会让这笔流水被某个物品「独占」；且日常小额消费被迫建物品

三个方案可以组合：先做 B 的对账提示（1 天）作为过渡，再实施 A。B 的提示逻辑在 A 落地后正好变成「未关联流水」的兜底展示，不会白做。
